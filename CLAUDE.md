# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A simulated Bitcoin + fiat brokerage ledger — API Gateway + a single Lambda function backed by two DynamoDB tables (`Accounts`, an append-only `Transactions` log), built with AWS SAM. It started as a minimal `Items` CRUD scaffold whose only job was to prove a full serverless CI/CD pipeline (build → local Docker smoke test → pytest unit+integration → deploy only if all of that passes → post-deploy smoke test against the live endpoint); the business logic layer was later replaced with a real ledger (idempotent transactions, atomic balance updates via `TransactWriteItems`, no negative balances under concurrency, an append-only audit trail, and a reconciliation endpoint) while keeping the exact same stack and pipeline.

The project journey is documented in `guides/` as six numbered guides (overview, environment setup, testing strategy, CI/CD pipeline, GitHub OIDC deploy setup, troubleshooting log) — mirroring the same pattern used in the sibling portfolio projects `sf-ebikes-test-automation` (`guides/`) and `hl7-interface-qa` (`docs/`). **After changing app code, the test suites, the Makefile, the CI workflow, or `bootstrap/github-oidc.yaml`, proactively check whether `guides/*.md`, this file, or `README.md` need updating too — don't wait to be asked.**

## Commands

```bash
make build              # sam build
make test-unit          # pytest tests/unit (moto-mocked DynamoDB, fast, no Docker)
make test-integration   # pytest tests/integration (spins up amazon/dynamodb-local in Docker)
make test               # both of the above
make test-local-invoke  # sam local invoke against the built artifact, wired to a
                         # Docker-networked DynamoDB Local (mirrors the CI smoke-check step)
make deploy              # sam deploy (uses samconfig.toml defaults)
make test-smoke          # pytest tests/smoke — requires API_BASE_URL env var pointing
                          # at a live, deployed API Gateway endpoint
```

Setup:

```bash
pip install aws-sam-cli
pip install --break-system-packages -r requirements-dev.txt   # or use a venv
# AWS CLI: https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html
```

If `make build` fails validating the `python3.12` runtime locally, use `sam build --use-container` instead — it builds inside an AWS-provided container matching the real Lambda runtime, sidestepping whatever Python version is actually installed on the local machine. See Guide 2.

## Architecture

- `template.yaml` — SAM template: `AccountsTable` (`account_id` PK) and `TransactionsTable` (`transaction_id` PK, plus an `AccountIndex` GSI on `account_id`+`executed_at` for per-account history/reconciliation queries), both `PAY_PER_REQUEST`; `LedgerFunction` (Python 3.12 Lambda, `DynamoDBCrudPolicy` scoped to both tables); six API Gateway routes (`POST /accounts`, `GET /accounts/{account_id}`, `GET /accounts/{account_id}/balance/verify`, `POST`/`GET /accounts/{account_id}/transactions`, `GET /price`). `Globals.Function.Environment.Variables` declares `DYNAMODB_ENDPOINT_URL` with an empty default purely so `sam local invoke --env-vars` has an existing key to override locally — SAM CLI only overrides template-declared environment variables, it silently drops anything else (see Guide 6, issue #6).
- `src/app.py` — single handler (`lambda_handler`) that routes on `httpMethod` + the API Gateway proxy event's `resource` template (needed since several routes share the same method/path-param shape). Two boto3 clients: `dynamodb`/`accounts_table`/`transactions_table` (resource-level, for `get_item`/`query`) and a separate `dynamodb_client` (low-level, for `transact_write_items` only — reusing `dynamodb.meta.client` there corrupts the payload, see Guide 6 issue #5). Patches `TypeSerializer.serialize` at import time (guarded to run once, `_patched_for_decimal`) so every `Decimal` — on both the low-level and resource-level write paths — serializes as fixed-point, not the scientific notation `str()` produces past a threshold and DynamoDB's Number type rejects outright (Guide 6 Part 3). Every BTC-denominated value is quantized to satoshi precision (`_quantize_btc`, 1e-8, `ROUND_DOWN`) at the one point it enters the system — not cosmetic: an unquantized value can need more significant digits to sum exactly than Python's default `Decimal` context preserves, causing false reconciliation mismatches against DynamoDB's own (higher-precision) server-side arithmetic. Core business logic: `create_account` (atomic `Accounts` row + synthetic `SEED` `Transactions` row), `create_transaction` (idempotent-via-`attribute_not_exists`, atomic funds-check-and-update via `TransactWriteItems`, with a retry loop for `TransactionConflict` — a real DynamoDB signal under genuine concurrent writes to the same item, distinct from a business-rule rejection), `verify_balance` (sums the full ledger from the `SEED` row forward and compares to the cached balance), `get_btc_price`/`_fetch_coinbase_price` (short-TTL-cached proxy to Coinbase's public exchange-rates endpoint, falling back to a stale cached price rather than ever crashing the transaction flow, and explicitly casting `rates.USD` from string to `Decimal`). Honors `DYNAMODB_ENDPOINT_URL` to point boto3 at a local DynamoDB endpoint instead of real AWS.
- `tests/unit/test_app.py` — exercises `app.lambda_handler` directly against a `moto`-mocked `Accounts`/`Transactions` (with GSI). No Docker, no network, sub-second. Covers idempotency, insufficient-funds rejection, reconciliation (fresh account, after transactions, and an injected mismatch), append-only enforcement, boundary math, and Coinbase failure/staleness handling — with `app._fetch_coinbase_price` monkeypatched to a fixed price everywhere except the dedicated string-vs-Decimal regression test.
- `tests/integration/` — `conftest.py` starts a real `amazon/dynamodb-local:3.3.1` Docker container (`-sharedDb`, session-scoped, pinned rather than `latest` — see Guide 2) and creates/tears down uniquely-named `Accounts`/`Transactions` tables (with GSI) per test via the `ledger_tables` fixture; `test_api_integration.py` runs a full account lifecycle, a duplicate-`transaction_id` check, and — the one test structurally impossible against `moto` — two real `BUY` requests fired from separate threads at the same account, confirming the atomic conditional write actually prevents an overdraft under genuine concurrency. One test (`test_full_lifecycle_against_real_dynamodb_and_coinbase`) hits the real Coinbase endpoint deliberately; every other test fixes the price via the same monkeypatch technique as the unit suite.
- `tests/smoke/test_smoke.py` — full ledger lifecycle (price check → create account → `BUY` → confirm duplicate rejection → verify reconciliation → confirm history), via `requests` against `API_BASE_URL` (the real deployed API Gateway stage). No delete-account endpoint exists (deliberate — real ledgers don't delete), so smoke-created accounts accumulate in the live environment, same as this portfolio's other suites that create real, un-cleaned-up records against live targets.
- `Makefile` — the single source of truth for how each step is actually run; both local dev and CI (`.github/workflows/ci-cd.yml`) call into it so the two never drift. `test-local-invoke` starts DynamoDB Local with `-sharedDb` (without it, the manually-created table and the invoked Lambda's own default credentials silently see two different, empty databases — Guide 6 issue #7) and verifies the actual response payload for an `errorType` key rather than trusting `sam local invoke`'s exit code, which is `0` even when the invoked function throws unhandled (Guide 6, the gap noted after issue #7).
- `events/get-account.json` + `env.local-invoke.json`: inputs for `make test-local-invoke` — a canned `GET /accounts/{account_id}` proxy event for a nonexistent account (enough to prove the built artifact boots and reaches DynamoDB, without needing Coinbase or pre-seeded data), and an env-var override file pointing `LedgerFunction` at `http://dynamodb-local:8000`.
- `.github/workflows/ci-cd.yml` — runs on PRs and pushes to `main`. Every run: `make build` → `make test-local-invoke` → `make test`. Only on a push to `main` does it additionally configure AWS credentials (via OIDC role assumption — no long-lived keys), `sam deploy`, look up the stack's `ApiEndpoint` output, and run `make test-smoke` against it. Guarded by a `concurrency` group so overlapping runs can't hit the same stack at once.
- `samconfig.toml` — default `sam deploy` parameters (stack name `aws-serverless-app`, `us-east-1`, `CAPABILITY_IAM`, S3 bucket auto-resolved).
- `bootstrap/github-oidc.yaml` — one-time, separately-deployed CloudFormation stack (`aws-serverless-app-github-oidc`, deployed manually with admin credentials, not by CI) creating the GitHub Actions OIDC provider and the `aws-serverless-app-github-actions-deploy` IAM role that `ci-cd.yml` assumes. Trust is scoped to `repo:korara78@<orgId>/aws-serverless-app@<repoId>:ref:refs/heads/main` — GitHub embeds immutable org/repo IDs in the OIDC `sub` claim alongside the names, so a trust policy written with just `repo:korara78/aws-serverless-app:ref:refs/heads/main` silently never matches (confirmed via CloudTrail on a real `AssumeRoleWithWebIdentity` `AccessDenied` event — this cost real debugging time, don't reintroduce it). The role's permissions are scoped to this app's own resource names (`aws-serverless-app-*`) plus two account-agnostic AWS-owned resources every SAM deploy needs regardless of app: `cloudformation:CreateChangeSet` on `arn:aws:cloudformation:*:aws:transform/Serverless-2016-10-31`, and full lifecycle (including `TagResource`/`DeleteBucket`) on the `aws-sam-cli-managed-default*` S3 bucket SAM's own `--resolve-s3` bootstrap creates.
